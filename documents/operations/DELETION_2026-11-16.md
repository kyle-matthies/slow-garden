# In-app deletion, 2026-11-16 (D-024)

Status: built, independently reviewed (APPLY AFTER FIXES; fixes below are in),
exercised locally. **Not applied to the hosted project, not deployed.**

Ship order is guarded by `GARDEN_DELETION_ENABLED` (server-side, default off,
see `applications/web/.env.example`). While off, no delete control or delete
section is rendered, every deletion action refuses, and the landing page keeps
the "deletion is not available yet" wording. The code can merge before the
migration is applied; turn the flag on only after the steps at the end.

## Decisions

- **Deletion is immediate. There is no 30-day tombstone.** This departs from
  the retention baseline in `PRIVACY_SECURITY_THREAT_MODEL.md` ("tombstone
  immediately; hard-delete after 30-day recovery window"). Chosen for the
  single-owner dogfood stage, where archive is the undo and export is the
  copy. Revisit before any external account exists, and amend the threat
  model or build the window then. To be copied into `DECISION_LOG.md` by the owner.
- **Account deletion needs a live session from a sign-in in the last ten
  minutes** (`auth.sessions` row matching the token's `session_id`, this
  user, not expired, `created_at` within ten minutes). Session creation time
  is used, not refresh time, because refresh happens without the person.
- **Direct `DELETE` on `gardens` and `seeds` is withdrawn** from
  `authenticated` (grant revoked, both `*_delete_own` policies dropped). The
  RPCs are the only way to erase. Grep found no direct delete in the web app,
  tests, scripts or the iOS client.
- **Hosted pre-checks that must pass before applying:**
  `has_table_privilege('postgres','auth.users','DELETE')` and
  `has_table_privilege('postgres','auth.sessions','SELECT')` are true for the
  function owner; and a backup or PITR restore point is confirmed to exist
  (the migration drops policies and changes grants).

## Design

Archive hides; delete erases. Deletion is five owner-only RPCs plus a read-only
preview, all in `supabase/migrations/20261116010931_in_app_deletion.sql`:

| RPC | Scope | Confirmation checked in the database |
|---|---|---|
| `delete_entry(p_entry_id)` | one entry, every revision | none |
| `delete_seed(p_seed_id)` | a thought and its entries | none |
| `delete_plot(p_plot_id, p_confirm_name)` | a topic and its thoughts | topic name |
| `delete_garden(p_garden_id, p_confirm_name)` | a garden | garden name |
| `delete_account(p_confirm)` | every garden, the account row, the sign-in identity | session email (or "delete my account" if the session has none) |
| `deletion_preview(p_kind, p_id)` | counts only; erases nothing | n/a |

- Each is `SECURITY DEFINER`, `set search_path=''`, acts only on rows whose
  `tenant_id = auth.uid()`, is revoked from `public` and `anon` and granted to
  `authenticated`. Definer is required: users hold no `DELETE` on `entries`,
  `plots` or immutable `seed_revisions`, and cannot read `private.pass_inputs`.
  This is a recorded exception to the threat model's "user-facing mutations
  avoid SECURITY DEFINER".
- One transaction per call: everything or nothing. A missing or foreign id
  returns `{"deleted": false}` (replay-safe, no existence oracle).
- The dialog's counts and the deletion's receipt come from the same function
  (`private.deletion_scope`).
- Account deletion removes `auth.users` inside the same transaction (sessions,
  identities and refresh tokens cascade). No service-role key is used by the
  web app. If the identity cannot be removed, the whole call fails and nothing
  is erased. A stale, expired, revoked or foreign session is refused with
  SQLSTATE `SGA01`; the dialog then explains, sends an email code, verifies it
  in place and returns to the filled-in confirmation.
- Every `delete_*` first locks the caller's `accounts` row, the lock
  `prepare_pass` takes, so deletion and pass preparation serialise.
- Lock order is always `private.pass_inputs` then `public.garden_passes`
  (rows by `pass_id`), matching `claim_garden_pass` and `finish_garden_pass`.
  A deadlock or lock timeout, if one still occurs, erases nothing and the UI
  asks for a retry.

### What is erased

| Store | Entry / thought | Topic | Garden / account |
|---|---|---|---|
| `entries`, `seed_revisions` (and its search index) | deleted | deleted | deleted |
| `seeds`, `plots`, `gardens`, `accounts`, `auth.users` | thought only | plus topic | plus garden; account also removes account and identity |
| `garden_passes` that read the writing | withdrawn or cancelled, kept as a content-free ledger row | deleted if scoped to the topic | deleted |
| `private.pass_inputs` snapshot, corrections, context | emptied for those passes | deleted | deleted |
| `blooms`, `bloom_responses`, `tending_marks`, `tending_mark_responses` of those passes | deleted | deleted | deleted |
| Copies in other passes: quoted evidence, pruned interpretations and labels in `corrections`; titles and labels in `context.index` | removed | removed | deleted |
| Provider batch and file ids | queued through the existing cleanup path | kept in `private.provider_orphans` | kept in `private.provider_orphans` |
| Unsaved drafts in the deleting browser | discarded | discarded | discarded |

A pass that read deleted writing loses **all** its blooms and marks, including
ones that quote other entries (existing behaviour, kept: the model read the
deleted text). The preview counts them.

### Runbook gap 3.9

`private.provider_orphans` (ids and scheduling only) is filled by a
`before delete` trigger on `private.pass_inputs` whenever cleanup is pending and
any provider id exists, on every path that removes a pass. The same trigger
settles an unsettled budget reservation (spent if work reached the provider,
released otherwise), which previously stayed reserved forever. Drain:
`claim_provider_orphan()` / `resolve_provider_orphan()` (service role only) and
`drainOrphan` in `supabase/functions/_shared/garden-runtime.mjs`, called by
`runOne` when no pass is due. An orphan is removed only after every file is
deleted; a provider error leaves it queued. A provider 404 counts as already
deleted. After twenty attempts an orphan is no longer claimed and stays, with
its ids, for an operator. A queue that cannot be read reports
`orphan_queue_unavailable`, never `idle`.

`runOne` also cleans up from memory when the ledger refuses to record an id
(the pass was deleted mid-dispatch): after upload it deletes the file; after
batch creation it cancels the batch and deletes the input file.

## Residual gaps

1. **Backups and storage internals.** Provider backups and WAL keep deleted
   rows until they expire; dead tuples persist until vacuum. The UI says so.
2. **Email in auth audit log.** `auth.audit_log_entries` rows naming the
   deleted account's email are not removed; that table belongs to Supabase
   Auth and is not touched here. Retention there should be set or purged by
   the operator.
3. **No stored deletion receipt (T-13).** The RPC returns counts to the
   caller; nothing durable records that a deletion happened.
4. **Definer RPCs in `public`.** Required for the Data API to reach them; the
   threat model prefers privileged functions in a private schema. Advisors
   will warn. Each checks `auth.uid()` and has an empty search path.
5. **Old access token.** After account deletion a still-valid access token
   (up to its expiry) authenticates but finds and can create nothing (tested).
6. **Provider output after an in-memory cancel.** When `runOne` cancels a
   batch the ledger never recorded, an output or error file the provider
   writes for it afterwards is not tracked anywhere.
7. **Stuck orphans** stop retrying after twenty attempts. Watch
   `select count(*), max(attempts) from private.provider_orphans`.
8. **Other browsers.** Only the deleting browser's drafts are discarded.
9. **Trigger cost.** The existing per-row `invalidate_source_passes` trigger
   scans all pass inputs; large account deletions will be slow at scale.
10. **Landing.** After account deletion the browser lands on `/account/deleted`
    (calm confirmation, link to `/`), not on `/` itself.
11. **Flag plumbing.** Delete controls ask the server once per page load
    whether deletion is on (a server action), because `GardenData` and
    `garden/page.tsx` are owned elsewhere. Passing it with the page data would
    be cleaner.
12. Docs still describing 3.9 as open (`AI_ACTIVATION_RUNBOOK.md`, the worker
    README) were not edited.

## Reversing this migration

No executable down-migration is provided, on purpose. If it must be reversed:

1. Turn `GARDEN_DELETION_ENABLED` off first, so no new deletion starts.
2. **Do not drop `private.provider_orphans` while it has rows.** Each row is
   the only record of provider files that still hold private text. Let the
   worker drain it to zero, or export the ids and delete the files at the
   provider by hand, and only then drop the table.
3. Do not drop the `pass_inputs_keep_orphan` trigger while any path can still
   delete a pass (a garden cascade, an operator). If it is dropped, ids and
   budget reservations of deleted passes are lost again (runbook gap 3.9).
4. Then, in a new reviewed migration: drop the six public RPCs and the private
   helpers; drop the orphan RPCs after the worker no longer calls them (an
   older worker reports `orphan_queue_unavailable`, harmlessly).
5. Restoring direct deletes (`grant delete on public.gardens, public.seeds to
   authenticated` and the two `*_delete_own` policies) brings back the
   unscrubbed path the review flagged; prefer leaving them withdrawn.
6. Deleted data is not restored by reversing the schema. Only a backup does that.
